## Why
Measured so far on 10 real pages / 127 blocks: component right on 48% of blocks today, 69% with "code cuts blocks -> decision model picks the component -> LLM fills one block per call (with retry)". Two problems remain. (1) The fill model spends 63-87% of its output on hidden reasoning, calls take a median of 26 s and some hang for minutes. (2) The largest group in every arm is "right component, content incomplete": text, images and items go missing when an LLM re-writes the page content into JSON.

A public project (browser-use/jev-ultrafast, MIT licence) shows a pattern that addresses both: turn what is on screen into a NUMBERED TABLE OF ELEMENTS; ask the decision model several questions in ONE request - what to do, and for each possibility, which numbered element is the target; use only the answer head that matches the chosen option; let CODE act on that exact element; call a small LLM with reasoning switched off only when text must be written. For import nothing needs writing: content is copied from the page.

## Arm B: `jev-points-code-copies` (no LLM at all)
Per code-proposed block (from `blocks.json`, exactly as `jev-then-llm-blocks` does):

1. **Element table.** From the block DOM subtree in the saved `page.html`, build an indexed table of content-bearing elements in document order: headings, paragraphs and text containers with their own text, links, buttons, images (including CSS background images that the saved production nodes expose), videos and iframes, form controls, list items. Each row: index, kind, heading level if any, visible text cut to 160 characters, whether it has an href or src, depth, and the id of the repeated group it belongs to (see 2). Cap at 250 rows by dropping the deepest duplicate-text rows first, and RECORD any cap.
2. **Repeated groups, found by code.** Sibling elements (two or more) with the same tag + class signature and similar inner structure form a group `G1..Gn` with its item count and a one-line sample of the first item. Nested groups are allowed (a menu with sub-menus); record the parent group.
3. **One decision request per block, several heads** (use `askPanel` or the client the way `picks.ts` does; one HTTP request; if the client cannot carry heads with different option sets, say so and use the fewest requests possible):
   - `component`: the same choice question `jev-pick` asks.
   - `heading`, `subheading`, `body`, `image`, `primaryAction`, `secondaryAction`: each a choice among the table row indices plus `NONE`. Each head is offered only compatible rows (image head: image and video rows; action heads: links and buttons; heading head: headings and short text rows).
   - `itemsGroup`: a choice among the repeated groups plus `NONE` - which repeated group holds the items of this block (cards, slides, menu links, logos, posts, steps, statistics).
   All heads are speculative: they do not know the component answer, and their instructions say so, as in the reference project.
4. **Item template (a second request, only when `itemsGroup` is not NONE).** Show the element table of the FIRST item and ask heads `itemTitle`, `itemText`, `itemImage`, `itemLink`, `itemMeta` (date, category or number), each a choice among that item rows plus `NONE`. Code then applies the RELATIVE PATHS of the chosen rows inside the item to every sibling item in the group; when a path does not resolve in an item, fall back to the first compatible element in that item and record the fallback.
5. **Code copies, never rewrites.** Text is the normalised visible text of the element; body and rich text keep inline links as HTML in the form the production normalisers accept for rich-text fields (inspect the production parser); image = absolute URL + alt; link = absolute URL + label. Nothing is generated.
6. **Assemble the component by field meaning, from the production contract.** For the chosen component type read its contract (`buildPromptContractBundle` and the schema summary the LLM arms already use) and map: heading-like fields from `heading`; sub-heading, lead, description, body and content-like fields from `subheading` and `body`; image, media and background fields from `image`; button, CTA and action fields from the actions; the required array field (cards, items, slides, features, posts, logos, menuItems, statistics, steps and so on) from the items, each item mapped the same way onto the array item contract, with SmartLink and MediaReference value shapes as production requires (reuse the production helpers the normalisers use). Write the mapping as ONE generic, table-driven mapper keyed on field names and types - no per-site logic and no per-component hand-written code beyond a small synonym table. Then run the production validator exactly as the LLM arms do. If validation fails, record why; with `--llm-fallback` hand that single block to the existing LLM fill (allowed types = the picked type) and mark it `filledBy: "llm-fallback"`; without the flag the block fails.
7. When the component pick is uncertain by the existing fixed rule (top choice less than twice the second), assemble for the top choice only and record the alternatives.

Everything saved per block: the table, the groups, the probabilities of every head, template paths, fallbacks, unmapped required fields, the validation result, `filledBy`. `run.json` adds counts: blocks filled by code, by LLM fallback, failed; decision requests; total decision latency.
